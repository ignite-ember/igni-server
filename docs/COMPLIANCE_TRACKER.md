# Compliance tracker

**This is the register you keep between audits.** One row per control,
with a status, the evidence, an owner and a review date.
[COMPLIANCE.md](COMPLIANCE.md) is the companion piece: it argues *why*
each control is or is not satisfied and is written to be read once. This
file is written to be updated.

Two properties make a tracker worth having rather than another document
that drifts:

1. **Every `Fnn` in the Evidence column must exist in
   [REVIEW_FINDINGS.md](REVIEW_FINDINGS.md)**, the public index of the
   pre-production review: what each finding was, and the tests that guard
   it. (The log itself, with its command output, is kept privately.) Enforced by
   `tests/test_compliance_tracker_is_current.py`, which also checks the
   statuses are from the allowed set and that no row claims `Verified`
   without evidence. A tracker whose evidence links rot is worse than no
   tracker — it reads as assurance.
2. **`Owner` is a role, never a person's name.** People change; the
   obligation does not. An empty owner is a finding in itself, and shows
   up as `— unassigned` below.

**Status vocabulary**, used exactly:

| Status | Means |
|---|---|
| `Verified` | Tested, with evidence. Not "reviewed the code". |
| `Partial` | The control exists and something material is missing. The gap is named in the row. |
| `Operator` | The self-hosted customer owns this. We must make it possible and document it; we cannot do it. |
| `Gap` | Not implemented. |
| `Process` | Organisational, outside this codebase. Listed so the register is complete, never marked Verified here. |

**Review cadence.** Every row carries `Last verified`. A SOC 2 Type II
observation window needs evidence *over a period*, so a row last verified
before the window opened is not evidence for it. Re-verify quarterly, and
after any change to the control's subject.

## The gaps, in the order to close them

**All closed.** This list began as four `Gap` rows and two `Partial`
ones, ordered by cost against what an auditor or a customer's DPO asks
for first. Every item is struck through, and they are kept rather than
deleted because the ordering's history is the useful part — including
where the estimate was wrong, which happened twice: AC-9 was already
built when this said it was not, and DP-2's plan named the one piece
that should not be built.

What remains in the register is `Process` — policy somebody has to write
and sign, which no amount of code produces — and `Operator`, which are
decisions a customer makes about their own deployment.

1. ~~**AC-8 — access review report.**~~ Built — F92.
2. ~~**DP-6 / DP-7 — retention and erasure for `webhook_events`.**~~
   Built — F93.
3. ~~**CM-8 — SBOM.**~~ Built — F95. Not the CI step it looked like: the
   portal needed a second SBOM because an image scan of it sees none of
   the npm packages compiled into the bundle.
4. ~~**DP-8 — data export for a subject access request.**~~ Built — F96.
   The rows were the easy half: Article 15 also grants the purposes,
   recipients and retention, and honouring it must not disclose the other
   authors who appear in the same webhook payload.
5. ~~**DP-5 — a test defending the air-gap claim.**~~ Built — F94, which
   also opened **DP-5a**: the CLI's `api_url` still ships a vendor host as
   its default. The product direction is that **no vendor endpoint exists**
   — a customer points the CLI at their own deployment and igni's routing
   is configured with where their requests go. That makes this a deletion
   plus a refusal path for an unset value, not a different literal, and it
   removes the whole category of "an unconfigured client talks to us".
   DP-5a was then closed by DEC-14: `api_url` ships empty and an unset
   value is refused with the setting's name.
6. ~~**LG-7 — monitoring and alerting.**~~ Built — F101. LG-6's
   fail-open write was indeed the first rule; the surprise was the
   second, which a test demanded rather than a person: every exposed
   metric must have a rule, and `igni_retention_failures_total` had
   none.
7. ~~**DP-2 — key rotation.**~~ Built — F106. Two settings rather than a
   list, because a list is ambiguous about which end is current. The
   estimate here was right about the shape and wrong about lazy
   migration, which is the part not to build: these rows are written
   when an admin registers an App, which may be never again, so lazy
   means possibly never.
8. ~~**AC-9 — OIDC against the customer's IdP.**~~ Built — F103, and it
   was built before this list said it was not. The audit was the work:
   no PKCE, a provider key rotation that broke every login for an hour,
   client authentication hardcoded to one of the two methods, a
   plaintext issuer accepted — and no sign-in button anywhere, which for
   the only provider an air-gapped deployment can reach made the whole
   feature unreachable.
