# igni server 0.8.1

The first release after 0.8.0. It changes no interface: the one change is
a fix to the SES email transport, so a deployment that sends mail through
Amazon SES with temporary AWS credentials no longer silently loses it. It
is a patch release — see the [changelog](../../CHANGELOG.md#081---2026-11-22).

## What you get

| Artefact | Where |
|---|---|
| API image | `ghcr.io/ignite-ember/igni-api:0.8.1` |
| Portal image | `ghcr.io/ignite-ember/igni-portal:0.8.1` |
| Helm chart | `charts/igni` (chart 0.3.0, appVersion 0.8.1) |
| Offline bundle | `igni-bundle-0.8.1.tar`, for air-gapped installs |

Each image is signed with the release cosign key and carries a CycloneDX
SBOM attestation. The offline bundle holds every image with its signature
and SBOM, the Helm chart and `igni-import`, under a MANIFEST signed with
the same cosign key — one key and one tool verify the whole bundle.
[OFFLINE_UPDATES.md](../OFFLINE_UPDATES.md) is how to verify either, and
where the public keys are published.

## Highlights

- **SES sends from temporary AWS credentials no longer silently fail.**
  `email_backend=ses` with credentials in the environment — the first
  link of the chain [docs/self-hosting.md](../self-hosting.md) documents,
  and how assume-role, SSO and every federated login hand out keys —
  passed `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` to boto3 as
  explicit static keys but never the `AWS_SESSION_TOKEN` that a temporary
  set requires. SES answered `UnrecognizedClientException: The security
  token included in the request is invalid`, swallowed inside the
  background send task, so the mail simply vanished with only an error
  line behind it. When static keys are in use and a session token is
  present, it is now forwarded with them — the whole set a temporary
  credential is. A long-lived IAM user's key has no token and is
  unchanged; the role/IMDS ambient path, where no keys are in the
  environment, is unaffected. Proven against real Amazon SES (us-east-1):
  before, the environment path returned the exception above; after, the
  same send returns a MessageId.

The full list is the [changelog](../../CHANGELOG.md#081---2026-11-22).

## Upgrading

An install made from 0.8.0 upgrades by moving its image tag to `0.8.1`;
the chart runs the database migrations as a `pre-upgrade` hook and stops
if they fail ([the chart's
README](../../charts/igni/README.md#upgrades)).

The chart did not change, so its own version stays `0.3.0`. This release
carries no database migration of its own and no new configuration: the
operational prerequisites of 0.8.0 — a writable, persisted
`IGNI_STATE_DIR`, and `INTEGRITY_REPORT_PUBLIC_KEY` for the sealed
integrity-report export — are unchanged and still described in
[v0.8.0.md](v0.8.0.md).

## Security

No security fix is part of this release, and no advisory has been
published against an earlier release. To report a vulnerability, see
[SECURITY.md](../../SECURITY.md).

## Verifying

```sh
cosign verify --key igni-cosign.pub --insecure-ignore-tlog=true \
  ghcr.io/ignite-ember/igni-api:0.8.1
igni-import --bundle igni-bundle-0.8.1.tar --public-key cosign.pub \
  --expect-version 0.8.1 --verify-only
```
