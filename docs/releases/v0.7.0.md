# igni server 0.7.0

The first release of igni server that has ever shipped, and it changes an
interface: the inference pools are gone, so the API answers one flat list
of nodes where it used to answer a list of pools. While the major version
is 0, a minor version may carry that — this one does, and its entry in the
changelog says so.

## What you get

| Artefact | Where |
|---|---|
| API image | `ghcr.io/ignite-ember/igni-api:0.7.0` |
| Portal image | `ghcr.io/ignite-ember/igni-portal:0.7.0` |
| Helm chart | `charts/igni` (chart 0.2.0, appVersion 0.7.0) |
| Offline bundle | `igni-bundle-0.7.0.tar`, for air-gapped installs |

Each image is signed with the release cosign key and carries a CycloneDX
SBOM attestation. The offline bundle holds every image with its signature
and SBOM, the Helm chart and `igni-import`, under a MANIFEST signed with
the same cosign key — one key and one tool verify the whole bundle.
[OFFLINE_UPDATES.md](../OFFLINE_UPDATES.md) is how to verify either, and
where the public keys are published.

## Highlights

- **Inference pools are gone.** igni server routes chat over the
  customer's own nodes and nothing else; CodeIndex runs its own nodes from
  its own configuration. A node no longer has `pools`, in registration,
  on the portal's node page or in storage, and `GET /v1/portal/inference`
  answers one flat list of nodes with one set of totals. **This changes
  the interface.**
- **The offline bundle is signed with cosign.** One public key
  (`cosign.pub`) and one tool (`cosign`) now verify the bundle, the
  images and the SBOMs. The MANIFEST's signature is `MANIFEST.sig` (was
  `MANIFEST.minisig`) and the bundle format is 2: an earlier
  `igni-import` refuses a format-2 bundle, so verify a new bundle with
  the `igni-import` from this release, or by hand with `cosign
  verify-blob`.
- **Personal API keys.** A person makes a key on the portal (*API keys*)
  and gives it to a program, which exchanges it at the token endpoint
  (`urn:igni:params:oauth:grant-type:api-key`) for a 15-minute session as
  them. A key's session cannot make keys, take a CLI session, sign a VM
  in or authorise a service.
- **The portal shows whose licence it is, and installs one.** A *Licence*
  page for super admins shows the licensee, the licence ID, its kind and
  issue date, and each paid module's state, expiry and message, and
  installs a licence file chosen or pasted there, with the reason when it
  is refused.
- **A refused client is told its registration's state.** When the token or
  revocation endpoint refuses a client because it is waiting for approval
  or has been revoked, the `401 invalid_client` answer carries
  `client_state`, so an SDK need not read `error_description`.
- **A new organisation's Default group holds igni's agents as they are
  now.** The seed is a copy of the agents and skills igni bundles; it had
  drifted, and a new member was warned about an agent nobody in their
  organisation had touched. It is copied from igni's core again, and the
  refreshed seed is carried to the organisations that already have a
  Default group.

## Upgrading

There is no earlier tagged release: 0.6.0 was prepared and never tagged,
so this is the first version that has ever shipped. An install made from
a build of `main` upgrades by moving its image tag to `0.7.0`; the chart
runs the database migrations as a `pre-upgrade` hook and stops if they
fail ([the chart's README](../../charts/igni/README.md#upgrades)).

Two changes need a word before the upgrade.

- **The bundle format is 2.** An `igni-import` from before this release
  refuses it. Verify a format-2 bundle with the `igni-import` from this
  release, or with `cosign verify-blob` by hand.
- **The chart's own version is 0.2.0.** The chart changed — the
  `artifacts:` block and its second Ingress and ConfigMap are gone, and
  the backup job gained flags — so upgrading the chart is a minor bump of
  its own. It is deliberately independent of the application version: a
  customer taking a fixed template need not move the image.

## Security

This release fixes two advisories in the base OS's zlib that the
scheduled vulnerability scan found in the image: CVE-2026-76844 (disclosure
via path traversal) and CVE-2026-85091 (a heap buffer overflow in
`gz_vacate()`). The image now installs the security update on top of its
base, and the base's Debian release is named in the tag rather than
inherited.

It also closes a disclosure in the token endpoint: the token and revocation
endpoints checked a client's registration state *before* its assertion's
signature, so an unsigned assertion naming any client id learned whether
that client was waiting for approval or revoked. The signature is verified
first now, and an assertion that does not verify is refused the same way
whatever the client's state.

No advisory has been published against an earlier release — none has been
published at all, because none has shipped. To report a vulnerability, see
[SECURITY.md](../../SECURITY.md).

## Verifying

```sh
cosign verify --key igni-cosign.pub --insecure-ignore-tlog=true \
  ghcr.io/ignite-ember/igni-api:0.7.0
igni-import --bundle igni-bundle-0.7.0.tar --public-key cosign.pub \
  --expect-version 0.7.0 --verify-only
```
