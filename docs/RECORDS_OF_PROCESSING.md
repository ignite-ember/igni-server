# Record of processing activities

**GDPR Article 30(1).** This is the vendor-supplied half of a record the *customer* keeps.

igni runs in the customer's own infrastructure and no data reaches the vendor, so the customer is the controller and there is no processor relationship to describe. What a controller cannot write without the vendor is the inventory: what the software stores, why, and for how long. That is what follows.

It covers **211 classified personal-data columns across 38 tables**, plus one table whose personal data lives in a JSON payload, grouped into 8 processing activities.

## Documents are processed by a paired service

Shared documents, their versions, the comments on them, their drafts and the requests to be let into them are **not** in this record. That processing moved to a separate deployment — the artifacts service — which holds those tables in its own database.

Said here rather than left as an absence, because a record of processing that quietly omits a category reads as a record that the category does not exist. A deployment running both services needs both records; one running only this service does not process that data at all.

What remains here about documents is the identity this server answers for the artifacts service — who somebody is and whether they are still a member, read from this server's directory with a token scoped to one organisation — and the notifications a document can cause, which are stored in this database because a person's notifications span more than documents. The artifacts service is a registered service like any other: it shares no secret with this server, and it is trusted only once a super admin approves it. An erasure or subject-access request made here is passed on to it and to every other approved service.

## Recipients and transfers

**Article 30(1)(d) recipients: none by default.** Nothing in the server sends personal data to a third party. Rules in each repository defend this rather than a promise: every outbound host named in code is on an allow-list with a reason, no vendor telemetry package may appear in a lock file (the OTLP exporters only, which send to the customer's own collector and have no default endpoint), and the check fails on its own staleness (`tests/test_nothing_phones_home.py`); a runtime test fails on any connection outside the network (`tests/test_igni_reaches_nothing_outside_the_network.py`). The scan has caught two real outbound requests since it was written (F94, F126). The recipients a deployment can acquire are the customer's choice: the model endpoint, a mail relay, an OpenTelemetry collector, and the web pages and search engine the client's agent may reach unless `air_gapped: true` is set (`docs/SUPPLIERS.md`, `docs/NETWORK_DIAGRAM.md`).

Services a super admin has approved — the artifacts service, CodeIndex — read members' names and addresses from this server's directory, one organisation at a time. They are deployments the customer runs, not third parties, so they belong in the controller's own record as further processing rather than as recipients; each keeps its own.

**Article 30(1)(e) third-country transfers: none,** for the same reason. The deployment talks to the source-control host the customer configured and to GPU nodes they registered — both their own choices, and both recorded in their own record as recipients if they wish.

## Article 30(1)(g) security measures

Not restated here. `COMPLIANCE_TRACKER.md` is the register, one row per control with a status and the evidence behind it, and it is asserted by a test rather than maintained by hand.

### Telling somebody that something concerns them

**Purpose (30(1)(b)).** Tell people about something that happened in an extension they use — a comment on their document, a request waiting on them — when the extension's service reports it. The service says what happened and who it concerns, by user id or address; this server resolves those to active members of the organisation the service's token is for, drops everybody else and the person who did it, writes one row per person once per event, and records when it reached their machine and when they read it. The source is recorded by this server from the extension the service uploaded, never taken from the request, so one service cannot speak as another.

**Legal basis (30(1)(b)).** `__CONTROLLER_TO_COMPLETE__`

**Categories of data subject (30(1)(c)).** People who are told — active members of the organisation a service names — and the people whose action is being reported.

**Retention (30(1)(f)).** For the life of the organisation. A notification that has been read is marked rather than deleted: deleting it would make "what have I already seen" unanswerable the first time two machines are open, and there is nothing in the row worth reclaiming.

### The cloud's producers and their VMs

**Purpose (30(1)(b)).** Run each producer — a person, an app an org admin registered, or a space the app declared for one of its own users — in a microVM of its own: which apps an organisation has and who owns them, which extensions each app has on, which VM profile each group and app gets and who defined it, the commands run as root in a producer's VM with who asked and what came of them, the messages, chats, actions and events services asked to deliver to a producer's agent or extension, with the thread key and the files that came with them, and which MCP servers a person approved, and the credential each producer's VM holds of its own — hashed, rotated on every use — so the platform never mints a token for anybody. Without these the platform cannot say who may run what in whose VM, or answer for it afterwards.

**Legal basis (30(1)(b)).** `__CONTROLLER_TO_COMPLETE__`

**Categories of data subject (30(1)(c)).** Members of an organisation who own or registered an app, defined a VM profile, asked for or were the target of a command, were sent an event, or approved an MCP server; the super admin who set the platform's caps or an organisation's quota; and an app's own users, named only by the id the app gives each of their spaces.

**Retention (30(1)(f)).** For the life of the organisation. Commands are the audit log of what ran in whose VM and are kept with it. An event waits at most `SERVICE_EVENT_MAX_WAIT_SECONDS` (14 days) to be delivered and is deleted `SERVICE_EVENT_RETENTION_DAYS` (30) after it was delivered, expired or dropped, by `app/services/retention.py`. A file a service sends with an item is deleted a day after upload if no item names it, and otherwise when its item expires. A VM credential is kept, revoked, for the life of the organisation as the record of who could reach a VM; it stops working after 90 days unused. The gateway's feed keeps one row per producer — whether they are one still, and when that changed. A member removed from an organisation has their VM's state, volume and keys erased after the organisation's `removed_member_retention_days` (default 30, at most the platform's maximum; 0 is at once), or at once on an erasure request; a legal hold an admin places stops that clock until it is released, and an erasure request is refused while it stands. Every erasure scheduled, moved or stopped is audited. An export of a removed member's data an admin asks for during retention is kept `PRODUCER_EXPORT_RETENTION_DAYS` (7) for the organisation to download. A feed row is kept `PRODUCER_FEED_RETENTION_DAYS` (30) after the erasure, by `app/services/retention.py`. A member who was only deactivated keeps their row while their suspended VM exists. A revocation telling the gateway and services to stop accepting a person's tokens is kept 31 days, past the longest a token lives. A mark naming a changed producer is deleted at the gateway's next poll.

## Tables that hold no personal data

The shared database holds these as well. None has a column that could name a person, so none is classified and no activity above claims it; they are listed so that this record accounts for every table rather than only the ones that hold personal data. All of them are in the shared plane's backup.

| Table | What it holds |
|---|---|
| `service_extensions` | The extension each registered service ships to people's machines: the bundle archive itself (up to 400 MiB of wheels), its manifest, a summary of its plugin, its digest and the service's signature over it. Software, uploaded by a service and distributed to every signed-in machine once a super admin approves the service. Removed with the registration it belongs to. |
| `extension_assets` | The files a registered service's extension runs that are not Python — a database distribution, a Java runtime, a model — one row per digest: the bytes (up to 1 GiB each), their size and the service's signature over them. Software, uploaded by a service beside its extension and distributed with it. Removed when no version the service holds declares it, or with the registration it belongs to. |
| `org_domains` | The email domains each organisation claims — `acme.com`, not anybody's address — which decide the organisation a new account joins. |
| `organisation_deletion_notices` | Which registered services have yet to confirm that an organisation was deleted: the deleted organisation's id, the service, how many calls went unconfirmed, when to call again and what the last call got back. No person is named. A row goes when its service confirms, or with the service's registration. |
| `revoked_grants` | Sign-ins a registered service has ended (RFC 7009 revocation): a random sign-in id, the client it was at, and when it was revoked and stops mattering. No person is named — the id is only in the refresh tokens the service held. Pruned once no refresh token of the sign-in can still be valid, 30 days at most. |
| `signing_keys` | The deployment's own token-signing keys: a key id, the public half, and the private half encrypted under `SECRET_ENCRYPTION_KEY`. Superseded keys are pruned once no token they signed can still be alive. |
| `tenants` | Which database holds each organisation's rows: an organisation id, a number, a database name and a state. The organisation itself is recorded under *Organisations and groups*. |

## A note on the columns marked withheld

A withheld column holds personal data and is deliberately not returned to the subject: a password hash, an OAuth token, the free-text detail of an audit entry that may name a third party. Withholding is a decision recorded column by column in `app/services/subject_access.py`, with the reason, and the subject-access report says that a value was withheld rather than pretending the column does not exist.

## A note on what is not in this record

**Repository content.** Source code, commit messages and the index built from them are not held by this server. Repository integration belongs to CodeIndex (igni__code-index), and the record of what it processes belongs with it.

**Model prompts and completions.** Not stored. A completion passes through the deployment to a GPU node the customer registered; what persists is the token count in `chat_usage`, not the text.
